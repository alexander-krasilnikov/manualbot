# Design

## Context

See proposal.md for why. Facts about the code that shape the approach:

- Every import ends in `IngestionService.enqueue(fileURL:title:id:)`. A caller-chosen `id` makes the same document one document across devices, and an existing id is left untouched. The bundled demo samples already use this (`sample-<slug>`).
- The 20 MB limit (`maxOriginalBytes`) is enforced there, from the file's size on disk, after a download would have finished.
- `ModelManifest.json` and `EmbedderCatalog.json` are bundled, decoded by a type in `Ports`, and read by `AppEnvironment`. The model downloader is built around `ModelSpec` and a mandatory checksum, so it does not fit.
- `DocumentRecord` is `Codable` and synced; a new optional field is backward compatible.
- `NetworkMonitor` exists in `App/Demo` and reports online/offline.
- Existing scripts in `scripts/` are one-file Swift or shell.

## Goals / Non-Goals

**Goals:**
- Importing from the catalog is the existing import, preceded by a safe download. No second ingestion path.
- Dedupe, "In library" state and cross-iPad behavior fall out of document identity, not new bookkeeping.
- The curated list can be re-verified and regenerated by one command, with the results readable in a terminal.

**Non-Goals:**
- Pasting an arbitrary URL, or updating the catalog over the air. The catalog ships with the app.
- Mirroring or bundling any PDF.
- Background downloads. Files are at most 20 MiB, so a foreground transfer is enough.
- Scheduled or CI runs of the script. It is a maintainer tool, run by hand.
- Search inside the catalog by document content. Only title, publisher and category are matched.

## Decisions

### 1. Catalog is bundled JSON, decoded like the model manifest
`ManualCatalog.json` in `App/Resources`, decoded by a `ManualCatalog` type in `Ports`. An entry holds `id` (a stable slug), `category`, `kind`, `title`, `publisher`, `language`, `url`, `bytes`, `pages`, `sha256`, `licenceNote`, `verifiedAt` and an optional `documentId`.
*Alternative:* a remote catalog. Rejected for now: it adds a server, a trust question and an offline story, and the user asked for a list prepared in advance. The script (decision 7) is how the list stays fresh between releases.

### 2. Document identity comes from the entry
A catalog document gets the id `catalog-<entryId>`. Passing it to `enqueue(id:)` gives dedupe, the "In library" state (the entry is imported when a library document has that id) and the same document on every iPad that syncs. A deleted document frees the id, so the entry returns to "not imported" with no extra code.
The two Couchbase entries that are also bundled demo samples set `documentId` to the sample id (`sample-couchbase-under-the-hood`, `sample-capella-architecture-overview`), so importing one from the catalog never creates a second copy of a bundled sample.
*Alternative:* a separate "imported from catalog" table. Rejected: it would drift from the library, especially after deletes and sync.

### 3. Origin is an optional field on the document record
`DocumentRecord.origin: DocumentOrigin?` holding `entryId` and `url`. Optional and `Codable`, so older records and older iPads read it as absent. The id already carries identity; the origin exists to show the publisher host and keep the address with the document.
*Alternative:* derive the host from the id alone. Rejected: the id does not hold the address, and the catalog can lose an entry after a rebuild.

### 4. A small foreground downloader, not the model downloader
A new port `ManualDownloading` with a `URLSession` adapter in `Adapters`:
- ephemeral configuration, no cookies, no stored credentials, an honest app User-Agent;
- streamed through a delegate, so the first bytes can be checked for `%PDF-` and a running count can abort the transfer past 20 MiB (a server that omits Content-Length is covered too);
- follows redirects but the final address must be HTTPS;
- writes to a temporary file named `<entryId>.pdf`, because `supportedType` reads the extension, then hashes it while streaming and hands the URL to `enqueue`;
- deletes the temporary file on every failure and after hand-off.
Hosts that refuse non-browser clients answer 403. The adapter does not impersonate a browser. It reports "this publisher does not allow automatic downloads" and the UI offers "Open in browser", after which the user imports the saved file with Files as usual.
*Alternative:* reuse `URLSessionModelDownloader`. Rejected: tied to `ModelSpec`, to a required checksum, and to background sessions whose resume machinery is not needed for 20 MiB.

### 5. A checksum mismatch warns, it does not block
Publishers re-issue manuals under the same address. Blocking would make the catalog brittle; ignoring the change would hide it. The entry imports and carries a note, and the script's `check` reports the drift so the record can be refreshed.

### 6. The catalog sheet
The toolbar's single Import button becomes a menu with "Files…" and "Manual catalog…". The empty library shows both. The sheet is a sidebar of categories, a kind filter and search, and a list with per-row state; multi-select imports several in one action. Row state is a pure function of the library's document ids and the in-flight downloads, held in a catalog view model like `LibraryViewModel`. Browsing makes no requests; the first download from a host shows a short notice naming it, remembered per host. Offline, importing is disabled with an explanation, using the existing network monitor (moved out of `Demo`).

### 7. The curation tool is one Swift script
`scripts/manual-catalog.swift` with `check`, `refresh` and `rebuild`, reading and writing `scripts/manual-catalog/curated.json` (selected entries, alternates, rejected) and generating `App/Resources/ManualCatalog.json`.
- Swift, not Python: the repo's scripts are Swift and shell, PDFKit gives page count, title and the first pages' text (needed for the military distribution-statement check), CryptoKit gives SHA-256, and `URLSession` behaves like the app's downloader, so a host that blocks the app also blocks the check.
- Requests are sequential per host with a pause, retry on 5xx and 429 (archive.org and OSTI both do this), and a clear User-Agent.
- Output is a per-category table and a final "N need attention" line; the exit status is non-zero when a selected entry fails.
- `rebuild` promotes a qualifying alternate of the same category and kind into a failing slot, sorts entries by category and title, and fails closed: validation errors leave the old file in place.
- Seed: the 182 researched entries (70 selected) in `seed/candidates.json` and 83 rejections in `seed/rejected.json` become the first `curated.json`. The prototype shell and Python tools the research used are not carried over.
*Alternative:* `curl`-based shell. Rejected: no PDF parsing, no checksums without extra tools, and poor error reporting across 180 entries.

### 8. No transport-security change
Only HTTPS addresses are allowed (script rule and downloader rule), so App Transport Security needs no exception.

## Risks / Trade-offs

- [Hosts block non-browser clients, so some entries fail in the app] → Select only entries that pass the script's check with the same kind of client; show "Open in browser" for the rest; re-run `check` before every release.
- [Links rot between releases] → Verified alternates per category and a one-command rebuild; the failure state is readable and does not leave partial files.
- [Copyright] → Link only, show the licence note, bundle nothing; Couchbase and manufacturer papers carry no redistribution grant.
- [The app now goes online outside the model downloads] → Disclose the host before the first download and send nothing about the user; browsing is request-free.
- [Cellular data: up to 20 MiB per entry] → The row shows the size before the user taps Import; a cellular warning is left as an open question.
- [Military entries] → Only public-release documents are selected, the script re-reads the distribution statement, and the military briefing decks are not formal catalogs.
- [The record gains a field] → Optional and defaulted, so older records and iPads keep working.

## Migration Plan

No data migration. Existing documents have no origin. Ship the catalog and the script in the same release; to roll back, remove the menu entry, the resource and the optional field, none of which existing data depends on.

## Open Questions

- Should the sheet warn before downloading on a cellular or low-data connection?
- Should a later release fetch an updated `ManualCatalog.json` from a published location, so entries can be replaced without an app update?
